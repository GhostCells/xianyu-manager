# 闲鱼选品评分 MVP 设计

版本：v1.0  
日期：2026-08-22  
状态：设计确认，尚未实现

## 1. MVP 目标和边界

### 1.1 目标

第一版选品评分 MVP 用于每天从指定关键词的闲鱼搜索结果中，找出更值得人工查看的候选商品，减少人工逐条浏览的时间。

系统定位是：

> **候选排序器，不是自动选品器。**

系统负责采集已确认的数据、计算可解释的相对分数，并将候选商品分层展示。最终是否制作、上架或跟进某个商品，仍由人工决定。

### 1.2 第一阶段包含

- 按关键词采集闲鱼搜索第一页。
- 保存商品基础信息和搜索批次信息。
- 对初筛后的少量商品低频访问详情页。
- 保存想要数、浏览量、收藏数等详情快照。
- 使用固定规则计算候选分数。
- 每个关键词输出少量优先候选，供人工复核。

### 1.3 第一阶段不包含

- 不使用 AI 自动决策。
- 不自动决定是否制作商品。
- 不自动上架、调价或复制同行商品。
- 不把想要数、浏览量或收藏数解释为销量。
- 不根据卖家累计已售推断单个商品销量。
- 不采集评论、卖家主页或更多详情字段。
- 不进行多关键词并发和高频详情访问。
- 不改变 xianyu-manager 的自动回复、自动发货和消息监听流程。

## 2. 数据流程

```text
创建每日关键词任务
→ 搜索闲鱼第一页
→ 保存搜索运行记录
→ 标准化商品基础字段
→ 按 item_id 去重
→ 标题相关性、价格和风险规则初筛
→ 每个关键词选择少量商品进入详情探索
→ 串行打开独立 Detail Page
→ 获取 wantCnt / browseCnt / collectCnt
→ 保存当次商品快照
→ 在同关键词、同批次内计算相对分数
→ 合并跨关键词重复商品
→ 输出候选分层清单
→ 人工查看并决定是否继续研究
```

建议第一阶段每个关键词只处理第一页，并限制详情页数量为 10～20 个。同一商品被多个关键词命中时，本轮只访问一次详情页。

详情访问失败、登录校验或平台验证均应记录明确状态，并停止对应访问；不得绕过平台验证，也不得将失败结果写成数值 0。

## 3. 数据来源

### 3.1 搜索页

已确认的搜索响应来源：

```text
mtop.taobao.idlemtopsearch.pc.search/1.0
```

原始商品列表路径：

```text
data.resultList
```

第一版使用字段：

| 字段 | 用途 |
|---|---|
| `item_id` | 商品唯一关联标识 |
| `title_raw` | 搜索卡片原始展示文本，用于相关性初筛 |
| `price` / `price_text` | 价格筛选与价格适配度 |
| `url` | 人工复核和详情访问 |
| `search_rank` | 记录商品在本次搜索中的位置 |

搜索响应中的 `title` 经常混合商品标题与大段描述，因此数据库统一按 `title_raw` 保存，不将其视为干净标题。

搜索页的 `wantNum` 已被实测为可能返回字符串 `"0"`，而同一商品详情页可以返回非零想要数。因此第一版评分不采用搜索页的 `wantNum` 作为可靠热度事实。

### 3.2 详情页

已确认的详情响应来源：

```text
mtop.taobao.idle.pc.detail/1.0
```

第一版使用字段：

| 字段路径 | 含义 |
|---|---|
| `data.itemDO.wantCnt` | 商品想要数 |
| `data.itemDO.browseCnt` | 商品浏览量 |
| `data.itemDO.collectCnt` | 商品收藏数 |

以下字段不进入第一版商品评分：

- `buyerDO.favored`、`buyerDO.isCollected`：仅表示当前登录账号的操作状态。
- `b2cItemDO.wantBuyCount`、`b2cItemDO.browseCnt`：与普通商品 `itemDO` 口径冲突。
- `sellerDO.hasSoldNumInteger`：卖家级数据，不是当前商品销量。
- 卖家导航接口中的 `soldCount`、`purchaseCount`：口径尚未验证。

## 4. 数据库设计

为了支持重复观察和增长分析，第一版至少需要商品主表、搜索运行表、观测快照表和评分记录表。本文仅定义建议结构，不代表数据库已经修改。

### 4.1 `selection_items`

保存商品身份和当前基础信息。

| 字段 | 类型 | 必须 | 用途 |
|---|---|---:|---|
| `item_id` | TEXT PRIMARY KEY | 是 | 闲鱼商品唯一标识 |
| `title_raw` | TEXT | 是 | 搜索卡片原始展示文本 |
| `canonical_url` | TEXT | 是 | 标准商品链接 |
| `first_seen_at` | DATETIME | 是 | 系统首次发现时间 |
| `last_seen_at` | DATETIME | 是 | 系统最近发现时间 |
| `created_at` | DATETIME | 是 | 本地记录创建时间 |
| `updated_at` | DATETIME | 是 | 本地记录更新时间 |

### 4.2 `selection_search_runs`

保存每一次关键词搜索。

| 字段 | 类型 | 必须 | 用途 |
|---|---|---:|---|
| `run_id` | TEXT PRIMARY KEY | 是 | 搜索运行唯一标识 |
| `keyword` | TEXT | 是 | 搜索关键词 |
| `page` | INTEGER | 是 | 页码，MVP 固定为 1 |
| `started_at` | DATETIME | 是 | 开始时间 |
| `finished_at` | DATETIME NULL | 否 | 完成时间 |
| `status` | TEXT | 是 | success / failed |
| `result_count` | INTEGER | 是 | 本轮解析商品数 |
| `source_api` | TEXT NULL | 否 | 上游接口名称和版本 |
| `http_status` | INTEGER NULL | 否 | 上游 HTTP 状态 |
| `error_code` | TEXT NULL | 否 | 失败诊断代码 |

### 4.3 `selection_item_snapshots`

保存每次观测时的商品数据。该表是增长分析的数据基础。

| 字段 | 类型 | 必须 | 用途 |
|---|---|---:|---|
| `snapshot_id` | INTEGER PRIMARY KEY | 是 | 快照编号 |
| `run_id` | TEXT | 是 | 对应搜索运行 |
| `item_id` | TEXT | 是 | 对应商品 |
| `keyword` | TEXT | 是 | 本次命中的关键词 |
| `observed_at` | DATETIME | 是 | 观测时间 |
| `search_rank` | INTEGER | 是 | 本关键词本页排名 |
| `title_raw` | TEXT | 是 | 当次搜索展示文本 |
| `price_cents` | INTEGER NULL | 否 | 数字价格，单位分 |
| `price_text` | TEXT NULL | 否 | 原始价格文字 |
| `price_parse_status` | TEXT | 是 | parsed / missing / unparseable |
| `want_count` | INTEGER NULL | 否 | 详情页想要数 |
| `browse_count` | INTEGER NULL | 否 | 详情页浏览量 |
| `collect_count` | INTEGER NULL | 否 | 详情页收藏数 |
| `detail_status` | TEXT | 是 | success / skipped / failed / verification_required |
| `detail_error_code` | TEXT NULL | 否 | 详情访问失败原因 |

建议约束：

```text
UNIQUE(run_id, item_id, keyword)
```

### 4.4 `selection_scores`

保存可复现的评分结果。

| 字段 | 类型 | 必须 | 用途 |
|---|---|---:|---|
| `snapshot_id` | INTEGER | 是 | 对应商品快照 |
| `score_version` | TEXT | 是 | 评分公式版本，例如 mvp-v1 |
| `want_rate_score` | REAL NULL | 否 | 想要率分项 |
| `collect_rate_score` | REAL NULL | 否 | 收藏率分项 |
| `browse_score` | REAL NULL | 否 | 浏览热度分项 |
| `relevance_score` | REAL | 是 | 标题相关性分项 |
| `price_fit_score` | REAL | 是 | 价格适配分项 |
| `total_score` | REAL NULL | 否 | 总分 |
| `missing_fields_json` | TEXT | 是 | 缺失字段列表 |
| `calculated_at` | DATETIME | 是 | 评分时间 |

### 4.5 空值原则

**未采集字段必须保存为 `NULL`。**

必须区分：

```text
未采集               → NULL
详情访问失败         → NULL + detail_status/error_code
接口真实返回 0       → 0
价格无法解析         → NULL + price_parse_status=unparseable
```

任何情况下都不能为了方便评分，把缺失的想要数、浏览量或收藏数自动填成 0。

## 5. 评分指标定义

第一版总分为 100 分。

| 指标 | 权重 | 定义 |
|---|---:|---|
| 想要率 | 35 | 想要行为相对于浏览规模的强度 |
| 收藏率 | 25 | 收藏行为相对于浏览规模的强度 |
| 浏览热度 | 20 | 当前市场关注规模 |
| 标题相关性 | 15 | 与搜索方向和目标商品类型的匹配程度 |
| 价格适配度 | 5 | 是否位于当前业务适合测试的价格带 |

### 5.1 平滑想要率

```text
smoothed_want_rate = (want_count + 2) / (browse_count + 100)
```

平滑参数用于抑制极小样本。例如 1 次浏览、1 次想要不应被解释为稳定的 100% 想要率。

### 5.2 平滑收藏率

```text
smoothed_collect_rate = (collect_count + 2) / (browse_count + 100)
```

想要和收藏可能存在平台语义重叠，因此分别评分，不把两者简单相加解释为独立用户数。

### 5.3 浏览热度

```text
browse_heat = ln(1 + browse_count)
```

使用对数降低超高浏览量老商品对排序的绝对支配。

### 5.4 标题相关性

第一版不使用 AI，使用可解释的词表规则：

| 命中类型 | 子项权重 |
|---|---:|
| 核心关键词 | 40% |
| 使用场景 | 25% |
| 目标用户 | 20% |
| 产品形态 | 15% |

排除词、明显无关实物、泛学习资料和高风险内容可以在评分前过滤，也可以按明确规则扣分。

### 5.5 价格适配度

价格只用于判断是否适合当前业务，不代表越贵或越便宜越好。初始价格带可暂定：

| 价格 | 适配度 |
|---|---:|
| 9.90～99.00 元 | 100 |
| 99.01～199.00 元 | 80 |
| 1.00～9.89 元 | 60 |
| 高于 199.00 元 | 40 |
| 无法解析 | 0，同时标记缺失/异常 |

价格带后续必须根据真实咨询和成交数据调整。

## 6. 评分公式

绝对指标在不同关键词之间不可直接比较。MVP 应先在“同一关键词、同一搜索批次”内计算百分位：

```text
P_want    = smoothed_want_rate 的批次内百分位
P_collect = smoothed_collect_rate 的批次内百分位
P_browse  = browse_heat 的批次内百分位
```

各项均转换为 0～1 后计算：

```text
total_score =
    P_want × 35
  + P_collect × 25
  + P_browse × 20
  + relevance_score × 15
  + price_fit_score × 5
```

其中 `relevance_score` 和 `price_fit_score` 也应转换为 0～1。

当详情数据缺失时，不应把缺失项按 0 分计算后伪装成完整评分。建议：

- 详情字段全部缺失：只做搜索初筛，不产生正式 `total_score`。
- 部分详情字段缺失：保存分项和缺失提示，候选清单标记“数据不完整”。
- 只有 `want_count`、`browse_count`、`collect_count` 均有明确数值时，才生成完整 MVP 总分。

## 7. 分数解释

评分表示：

> 该商品在本次同关键词候选中，表现出的相对关注度、意向率和业务匹配程度。

评分不表示：

- 实际销量。
- 实际利润。
- 商品一定能成交。
- 商品值得直接复制。
- 卖家的经营能力。
- 未来表现保证。

浏览量代表被查看的规模，想要数和收藏数代表平台记录的互动意向。三者都不能单独或组合解释为销量。

候选清单应同时展示原始数据、分项得分、缺失状态和推荐原因，避免只展示一个无法解释的总分。

## 8. 候选分层规则

| 总分 | 分层 | 处理建议 |
|---|---|---|
| 75～100 | 优先人工查看 | 当天进入人工研究清单 |
| 60～74.99 | 观察候选 | 继续观察下一次快照 |
| 40～59.99 | 暂不优先 | 保留数据，不主动推荐 |
| 0～39.99 | 忽略 | 默认不进入候选清单 |

建议每天每个关键词最多展示 5 条优先候选。跨关键词重复商品合并展示，同时保留所有命中关键词和各关键词排名。

规则还应包括：

- 数据不完整的商品不得进入“高置信优先”分层。
- 高分商品如果命中版权、违规、售后或技术门槛风险，应单独标记，不自动推荐制作。
- 人工可以标记“关注、暂缓、不做”，避免系统每天重复推荐已明确拒绝的商品。

## 9. 当前限制

1. 当前没有可靠的商品发布时间，无法按商品年龄校正累计互动。
2. 当前没有单品销量，不能计算真实转化率。
3. 当前没有评论数量和正文，无法判断用户反馈和售后问题。
4. 搜索页 `wantNum` 与详情页 `wantCnt` 可能不一致，评分必须采用详情页字段。
5. 收藏和想要的业务语义可能重叠，不能当成完全独立人数。
6. 浏览量、想要数、收藏数都是累计值，单次快照容易偏向上架时间较长的商品。
7. 同一关键词第一页只反映平台当前排序，不代表完整市场。
8. 价格区间和标题规则仍需用后续真实经营数据校准。
9. 详情访问会增加平台请求，必须保持低频、串行并监控登录验证状态。
10. 当前评分只能发现值得人工查看的候选，不能判断一定可复制、可盈利或适合上架。

## 10. 后续迭代方向

### 10.1 历史快照指标

以下指标必须依靠至少两次快照：

- 24 小时想要增长量和增长速度。
- 24 小时收藏增长量和增长速度。
- 24 小时浏览增长量和增长速度。
- 每千次新增浏览带来的新增想要数。
- 价格变化。
- 搜索排名变化。
- 连续出现天数和热度持续性。
- 商品下架或消失状态。

示例：

```text
24小时想要增速 =
  (本次 want_count - 上次 want_count)
  / 实际间隔小时 × 24
```

```text
每千次新增浏览想要数 =
  新增 want_count / 新增 browse_count × 1000
```

增长数据稳定后，可逐步提高增长速度权重，降低累计浏览量权重，从而减少老商品优势。

### 10.2 评分校准

- 根据人工“关注/不做”结果检查评分是否符合实际判断。
- 根据自己商品的咨询和成交数据调整价格带。
- 对不同赛道设置独立词表和阈值。
- 记录评分版本，确保历史结果可以复现。

### 10.3 暂缓事项

在基础快照数据尚未验证前，暂缓：

- AI 爆品判断。
- 自动制作和自动上架。
- 评论情感分析。
- 卖家画像评分。
- 多页高频采集。
- 多关键词并发。
- 用单一总分替代人工复核。

## 结论

第一版 MVP 应优先建立可信、可复现的“搜索发现—详情补充—快照保存—规则评分—人工复核”闭环。其价值是缩小人工查看范围，而不是替用户做最终选品决策。所有缺失字段必须保存为 `NULL`，所有互动指标必须按其真实含义展示，尤其不能把浏览量、想要数、收藏数或卖家累计已售解释为当前商品销量。
