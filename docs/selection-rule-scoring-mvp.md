# 闲鱼选品规则评分 MVP 设计

版本：v1.0  
日期：2026-08-23  
状态：仅设计，尚未开发

## 1. 评分目标

第一版规则评分系统用于：

> 在同一关键词、同一采集批次的候选商品中，按照可解释的固定规则进行相对排序，缩小人工审核范围。

系统定位必须明确：

> **第一版评分只是候选排序器，不是自动选品器。**

评分结果用于回答：

- 哪些候选更值得优先打开查看。
- 候选靠前主要是因为互动意向、关注规模、标题相关性还是价格适配。
- 哪些候选因数据缺失无法形成完整评分。
- 规则排序与后续人工判断是否一致。

评分结果不能直接回答：

- 商品是否一定能卖。
- 商品实际销量是多少。
- 商品是否能盈利。
- 是否应该直接复制、制作或上架。
- 是否符合平台规则、版权要求和当前交付能力。

任何制作、测试或上架决定仍由人工完成。

## 2. MVP 边界

第一版包含：

- 使用当前已确认的搜索、详情和人工审核数据。
- 使用固定公式生成 0～100 的相对分数。
- 保存分项分数、总分、评分版本和缺失字段。
- 同关键词、同批次内排序。
- 将高分候选交给人工复核。
- 用人工审核结果评估规则质量。

第一版不包含：

- 不调用 AI。
- 不自动改变 `candidate_status`。
- 不自动标记“值得测试”或“不值得测试”。
- 不自动制作、上架、调价或复制商品。
- 不修改采集频率和关键词配置。
- 不访问评论、卖家主页或额外详情接口。
- 不把浏览、想要、收藏解释为销量。
- 不使用自己的成交结果直接回写当次历史评分。

## 3. 输入数据

### 3.1 `selection_items`

使用字段：

| 字段 | 用途 |
|---|---|
| `item_id` | 商品唯一标识和跨快照关联 |
| `title_raw` | 规则相关性分析 |
| `canonical_url` | 人工复核入口 |
| `first_seen_at` | 系统首次发现时间，仅作背景信息 |
| `last_seen_at` | 最近被搜索发现时间 |
| `candidate_status` | 人工审核结果；不进入当次评分公式 |
| `candidate_status_updated_at` | 人工反馈时间边界 |

`title_raw` 当前可能混合标题和较长商品描述，因此相关性规则只能作为辅助项，不能赋予过高权重。

### 3.2 `selection_item_snapshots`

第一版主要输入：

| 字段 | 用途 |
|---|---|
| `run_id` | 确定同一搜索批次 |
| `item_id` | 关联商品 |
| `keyword` | 确定同关键词比较组 |
| `observed_at` | 评分数据时间 |
| `search_rank` | 仅展示，不直接作为热度事实 |
| `price_cents` | 价格适配度 |
| `price_parse_status` | 判断价格是否可靠 |
| `want_count` | 想要互动累计值 |
| `browse_count` | 浏览累计值 |
| `collect_count` | 收藏互动累计值 |
| `detail_status` | 判断详情数据是否有效 |
| `detail_observed_at` | 详情数据实际采集时间 |

只有 `detail_status='success'` 的详情数据才可进入完整评分。

以下情况不能伪装成 0：

```text
未补采       → NULL
补采失败     → NULL + failed
平台验证中止 → NULL + verification_required
接口真实返回0 → 0
```

### 3.3 `selection_item_reviews`

人工审核记录用于规则评估，而不是当次评分输入。

使用字段：

- `previous_status`
- `new_status`
- `reason_code`
- `reviewed_at`
- `related_snapshot_id`
- `related_search_run_id`

用途：

- 检查高分候选是否更常被人工标为“值得测试”。
- 统计低分商品是否仍被人工选择测试。
- 查找规则遗漏的商品类型。
- 根据人工否决原因调整相关性、价格和风险规则。

禁止把 `worth_testing` 直接转换成加分项，否则评分会被人工结果反向污染。

### 3.4 `selection_scores`

现有字段与第一版分项对应：

| 字段 | 内容 |
|---|---|
| `snapshot_id` | 被评分的快照 |
| `score_version` | 公式版本，例如 `rule-mvp-v1` |
| `want_rate_score` | 想要率分项，0～100 |
| `collect_rate_score` | 收藏率分项，0～100 |
| `browse_score` | 浏览热度分项，0～100 |
| `relevance_score` | 相关性分项，0～100 |
| `price_fit_score` | 价格适配分项，0～100 |
| `total_score` | 加权总分，0～100；数据不足时为 NULL |
| `missing_fields_json` | 缺失或无效字段列表 |
| `calculated_at` | 计算时间 |

同一快照可以保存多个评分版本，但同一个 `snapshot_id + score_version` 只能有一条记录。

## 4. 评分资格

### 4.1 完整评分条件

商品必须同时满足：

1. `detail_status='success'`。
2. `want_count IS NOT NULL`。
3. `browse_count IS NOT NULL`。
4. `collect_count IS NOT NULL`。
5. 三项数值均不小于 0。
6. `browse_count > 0`。
7. 能确定 `keyword` 和 `run_id`。

满足后才能生成完整 `total_score`。

### 4.2 不完整数据处理

| 情况 | 处理方式 |
|---|---|
| 互动字段缺失 | 保存已有分项，`total_score=NULL` |
| `browse_count=0` | 互动率无法计算，`total_score=NULL` |
| 价格缺失或无法解析 | `price_fit_score=0`，在缺失字段中标记；仍可形成总分 |
| 标题为空 | `relevance_score=0` 并标记异常 |
| 比较组样本不足 | 不产生正式总分，标记 `insufficient_cohort` |

建议同关键词、同批次至少有 5 条完整详情样本才生成临时分数，至少 10 条才认为排序具有基本参考价值。

样本不足时可以展示原始数据，但不能使用看似精确的总分误导人工。

## 5. 比较范围

第一版只在以下范围计算百分位：

```text
同一个 run_id
+ 同一个 keyword
+ detail_status='success'
+ 三项互动字段完整
```

原因：

- 不同关键词对应的市场规模不同。
- 不同日期的平台推荐和搜索结果会变化。
- 累计浏览量无法直接跨商品年龄比较。
- 同批次相对位置比全局固定阈值更容易解释。

因此：

- `skill` 的 80 分不能直接理解为强于 `ComfyUI` 的 75 分。
- 分数表示在各自比较组中的相对位置。
- 跨关键词候选合并时，应同时展示关键词、批次、原始指标和分项。

## 6. 指标定义

### 6.1 平滑想要率

```text
smoothed_want_rate = (want_count + 2) / (browse_count + 100)
```

用途：观察想要互动相对于浏览规模的强度。

为什么平滑：

- 1 次浏览、1 次想要不应被解释为稳定的 100%。
- 小浏览样本波动极大。
- `+2 / +100` 用于降低小样本的偶然优势。

在同批次内转为百分位：

```text
want_rate_score = percentile_rank(smoothed_want_rate) × 100
```

### 6.2 平滑收藏率

```text
smoothed_collect_rate = (collect_count + 2) / (browse_count + 100)
```

同批次百分位：

```text
collect_rate_score = percentile_rank(smoothed_collect_rate) × 100
```

收藏和想要可能存在语义重叠，因此分别观察，但不能解释为两类完全独立的购买用户。

### 6.3 浏览热度

先做对数变换：

```text
browse_heat = ln(1 + browse_count)
```

再转换为同批次百分位：

```text
browse_score = percentile_rank(browse_heat) × 100
```

对数变换用于降低超高累计浏览老商品的支配力。

浏览热度只表示被查看的累计规模，不是购买需求或销量。

### 6.4 标题相关性

第一版不使用 AI，采用确定性词表规则。

建议将每个关键词配置为：

```text
核心需求词
使用场景词
目标用户词
产品形态词
排除词
```

相关性分项：

| 子项 | 权重 |
|---|---:|
| 核心需求词命中 | 40 |
| 使用场景词命中 | 25 |
| 目标用户词命中 | 20 |
| 产品形态词命中 | 15 |

基础计算：

```text
relevance_score = 各子项命中得分之和 - 排除词扣分
```

最终限制在 0～100。

规则要求：

- 同一个词只在一个子项计分一次。
- 大小写和首尾空格规范化。
- 不能因为标题重复堆词而重复加分。
- 排除词命中只降低相关性，不自动决定“不值得测试”。
- 当前 `title_raw` 可能包含长描述，相关性权重不宜过高。

### 6.5 价格适配度

价格适配度表示是否适合当前闲鱼数字商品业务进行低成本测试，不表示越便宜越好。

第一版建议价格带：

| 价格 | `price_fit_score` |
|---|---:|
| 9.90～99.00 元 | 100 |
| 99.01～199.00 元 | 80 |
| 1.00～9.89 元 | 60 |
| 高于 199.00 元 | 40 |
| 低于 1 元 | 20 |
| 缺失或无法解析 | 0 |

价格带只是初始业务假设，后续应依据自己的真实咨询、成交、退款和售后数据调整。

## 7. 分项权重建议

第一版建议：

| 分项 | 权重 | 原因 |
|---|---:|---|
| 想要率 | 35% | 表示相对浏览规模下的想要互动强度 |
| 收藏率 | 25% | 表示相对浏览规模下的收藏互动强度 |
| 浏览热度 | 20% | 保留市场关注规模，但避免成为绝对主导 |
| 标题相关性 | 15% | 避免无关高热商品排到前面 |
| 价格适配度 | 5% | 只作轻量业务适配，不让价格替代需求判断 |
| 合计 | 100% | — |

总分：

```text
total_score =
    want_rate_score × 0.35
  + collect_rate_score × 0.25
  + browse_score × 0.20
  + relevance_score × 0.15
  + price_fit_score × 0.05
```

该权重是观察期初始值，不是已被成交数据验证的最优公式。

前 14～30 天应固定 `score_version='rule-mvp-v1'`，不要频繁改权重。需要调整时创建新版本，不覆盖旧分数。

## 8. 百分位计算建议

同批次数据按指标从低到高排序，推荐使用平均秩处理并列值：

```text
percentile_rank = (average_rank - 1) / (sample_count - 1)
```

特殊情况：

- 全部数值相同：所有商品该项记 50 分，而不是 0 或 100。
- 样本只有 1 条：不生成正式总分。
- 样本少于 5 条：保存分项为诊断结果，但 `total_score=NULL`。
- 完整样本 5～9 条：允许生成临时分数，标记低置信度。
- 完整样本不少于 10 条：正常生成规则分数。

并列处理必须稳定，不能因数据库返回顺序导致分数变化。

## 9. 分数解释

建议分层只用于安排人工查看顺序：

| 总分 | 展示层级 | 人工动作 |
|---|---|---|
| 75～100 | 优先查看 | 当天优先人工复核 |
| 60～74.99 | 候选观察 | 查看原始指标和商品内容 |
| 40～59.99 | 普通候选 | 有时间再看或等待下一次快照 |
| 0～39.99 | 低优先级 | 默认靠后展示，不自动否决 |
| `NULL` | 数据不足 | 不参与排序，等待补采或更多样本 |

分数的正确解释：

> 该商品在本次同关键词候选中，表现出的相对互动强度、关注规模和业务匹配程度。

分数的错误解释：

- 80 分等于 80% 成交概率。
- 80 分商品销量更高。
- 高分商品一定值得复制。
- 低分商品一定没有市场。
- 高分可以替代版权、交付和售后审查。

候选列表必须同时展示：

- 总分和评分版本。
- 五个分项。
- 原始 `want_count / browse_count / collect_count`。
- 价格。
- 关键词和批次。
- 缺失字段。
- 当前人工审核状态。

禁止只展示一个总分。

## 10. 如何结合人工审核结果

### 10.1 人工审核不进入当次公式

`selection_item_reviews` 不直接给商品加分或扣分。

原因：

- 人工结论是评估标签，不是市场事实。
- 如果“值得测试”直接加分，系统会循环证明人工决定正确。
- 历史人工判断可能受到当时资源、兴趣和风险偏好的影响。

### 10.2 规则效果观察

至少积累 30 条人工审核记录后，按评分区间统计：

```text
人工值得测试率 =
  new_status='worth_testing' 的商品数
  / 已完成首次人工审核的商品数
```

按分数层级观察：

| 评分层级 | 人工审核数 | 值得测试 | 不值得测试 | 已测试 | 已成交 |
|---|---:|---:|---:|---:|---:|

重点检查：

- 高分区是否更常被标为值得测试。
- 高分但不值得测试的主要原因。
- 低分却被人工测试或成交的漏判案例。
- 哪些关键词的分数与人工判断偏差最大。

### 10.3 原因代码用于规则修订

示例：

- 高分商品大量因 `irrelevant` 被否决：相关性词表需要调整。
- 高分商品大量因 `copyright_risk` 被否决：未来可增加独立风险过滤，但不应伪装成销量评分。
- 高分商品大量因 `high_support_cost` 被否决：可以新增交付适配维度，但需要人工可解释规则。
- 低分商品出现真实成交：检查小样本平滑、关键词比较组和价格权重。

规则调整必须发布新版本，例如：

```text
rule-mvp-v1
rule-mvp-v2
```

旧分数不覆盖，确保历史可复现。

### 10.4 时间边界与防止信息泄漏

评估某次评分时，只使用评分计算之后发生的人工审核结果。

```text
reviewed_at > calculated_at
```

不能使用早于评分时间的人工状态来证明该评分有效；否则属于数据泄漏。

## 11. 如何避免把互动指标误认为销量

### 11.1 明确字段名称

始终使用：

- 想要数 `want_count`
- 浏览数 `browse_count`
- 收藏数 `collect_count`
- 想要率 `want_rate`
- 收藏率 `collect_rate`

禁止命名为：

- 销量
- 成交量
- 转化率
- 购买人数
- 收入

### 11.2 UI 和报告说明

任何评分报告必须显示：

> 想要、浏览和收藏是平台累计互动指标，不代表真实销量、成交或利润。

“已成交”仅表示自己的测试商品出现了人工确认的真实成交，与同行候选商品销量无关。

### 11.3 不推算不存在的数据

禁止：

- 用 `want_count × 某个比例` 推算销量。
- 用卖家累计已售推算当前商品销量。
- 用浏览量和价格推算收入。
- 将收藏与想要简单相加解释为独立人数。
- 将补单或测试订单计为规则验证成交。

### 11.4 分数命名

推荐名称：

```text
候选优先分
规则排序分
人工查看优先级
```

避免名称：

```text
爆品概率
成交概率
赚钱指数
销量预测
```

## 12. 累计指标偏差与历史快照

当前缺少可靠发布时间，累计互动天然偏向存在时间更长的商品。第一版通过以下方式减轻但不能消除：

- 使用互动率而不是只看累计想要数。
- 对浏览量使用对数变换。
- 在同关键词、同批次内计算百分位。
- 降低单纯浏览热度的权重。
- 报告中同时展示原始数据。

积累至少两次有效快照后，可以计算：

```text
delta_want = 本次 want_count - 上次 want_count
delta_browse = 本次 browse_count - 上次 browse_count
delta_collect = 本次 collect_count - 上次 collect_count
```

标准化到 24 小时：

```text
want_growth_24h = delta_want / delta_hours × 24
browse_growth_24h = delta_browse / delta_hours × 24
collect_growth_24h = delta_collect / delta_hours × 24
```

增长指标在第一版只观察，不进入 `rule-mvp-v1`，原因是当前历史样本量不足且 `selection_scores` 尚无增长分项字段。

待连续积累 14～30 天后，再设计 `rule-mvp-v2` 的增长权重。

## 13. 评分执行流程

未来实现时的建议流程：

```text
输入 run_id
→ 查询该批次快照
→ 过滤详情成功且互动字段完整的商品
→ 检查比较组样本量
→ 计算平滑想要率与收藏率
→ 计算浏览量对数
→ 在同关键词同批次内计算百分位
→ 执行标题相关性规则
→ 执行价格适配规则
→ 计算分项和总分
→ 写入 selection_scores
→ 按 total_score 排序
→ 展示原始字段、分项和人工状态
```

评分过程：

- 不修改 `selection_items.candidate_status`。
- 不新增审核记录。
- 不触发采集或浏览器。
- 不覆盖其他 `score_version`。
- 相同输入和相同版本必须得到相同结果。

## 14. 评分质量检查

每次规则版本上线前至少验证：

1. 空值没有被转成 0。
2. 全部相同值时百分位稳定。
3. 并列值采用相同分数。
4. 不同数据库返回顺序不影响分数。
5. 总分始终在 0～100。
6. 权重之和严格为 100%。
7. 样本不足时 `total_score=NULL`。
8. 同一快照和版本重复计算具备幂等性。
9. 评分不会修改人工状态。
10. 报告不使用销量、成交概率等误导性名称。

## 15. 未来 AI 优化方向

AI 只应在规则评分稳定、人工反馈足够后作为辅助层，不替代原始数据和人工决策。

### 15.1 标题与商品语义清洗

当前 `title_raw` 可能混合标题和详情。未来 AI 可以：

- 提取真实商品名称。
- 区分商品主体、赠品和描述。
- 判断是否与搜索意图相关。
- 输出可解释的相关性理由。

AI 结果应单独保存，不覆盖 `title_raw`。

### 15.2 人工否决原因归类

AI 可以辅助将自由备注归类为：

- 版权风险
- 平台风险
- 交付困难
- 售后过重
- 需求不清
- 与现有商品重复

归类结果需要人工确认，不能自动更改候选状态。

### 15.3 候选摘要

未来可以让 AI 根据已有事实生成：

- 为什么排在前面。
- 主要数据优势。
- 数据缺失和风险提示。
- 建议人工重点核查的问题。

AI 摘要必须引用具体字段，不允许编造销量或利润。

### 15.4 规则调权建议

积累足够人工审核和真实测试结果后，AI 可以分析：

- 哪些分项与“值得测试”更相关。
- 哪些原因导致高分商品被否决。
- 不同关键词是否应使用不同价格带或相关性词表。

AI 只能提出调权建议；新权重仍需人工批准并发布新的 `score_version`。

### 15.5 暂不采用的 AI 能力

- 自动决定商品是否制作。
- 自动把候选改为值得测试。
- 自动预测销量或利润。
- 自动复制同行文案和素材。
- 自动绕过版权、平台或交付审核。
- 用模型结论覆盖人工审核历史。

## 16. 观察期与上线条件

在开发评分代码前，建议至少满足：

- 连续稳定采集 14 天以上。
- 主要关键词每个至少积累 30 条完整详情样本。
- 至少 30 条人工首次审核记录。
- 搜索成功率和详情成功率达到可接受水平。
- 三项互动字段联合完整率稳定。
- 已明确相关性词表和价格带初始配置。

如果样本不足，先继续采集和人工审核，不应因为有公式就提前上线自动排序。

## 17. 结论

`rule-mvp-v1` 应使用平滑想要率、平滑收藏率、对数浏览热度、确定性标题相关性和价格适配度五个分项，在同关键词、同批次内进行相对排序。

人工审核记录用于验证和修正规则，不直接进入当次分数。所有分项必须可解释，缺失字段必须保留为 `NULL`，互动指标必须始终按互动含义展示，不能称为销量、成交率或赚钱能力。

第一版评分的唯一作用是安排人工查看顺序，最终选品、测试、上架和经营决策仍由人工完成。
